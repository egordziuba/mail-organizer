# Скрытая почтовая автоматизация: запуск и управление

Проект: корень этого репозитория.

## Реализованная схема

**Windows Task Scheduler → скрытый Python worker → проверяемые команды → Hermes для управления/разбора.**

Выживание процесса не зависит от открытого Hermes Desktop или текущей беседы. Фоновый worker сам не запускает модель и не открывает браузер для авторизации. Затраты на модель возникают только при отдельном смысловом разборе.

### Файлы

- `runtime.json` — открытая конфигурация без токенов: архив, состояние, интервалы, три account slots.
- `src/mailorganizer/runtime.py` — цикл, heartbeat, управление, singleton.
- `src/mailorganizer/processes.py` — Windows Job Object для команды выгрузки; тайм-аут завершает именно её дерево, включая дочерний процесс venv-launcher.
- `src/mailorganizer/windows_task.py` — XML определения нашей задачи Windows.
- `scripts/register_worker_task.ps1` — регистрация без перезаписи чужой задачи.
- `scripts/mail_commands.py` — узкий командный мост для Hermes.
- `AGENTS.md` — правила работы Hermes в этом проекте.
- `.runtime/worker.json` — heartbeat + идентичность реального процесса + последний цикл.
- `.runtime/last_cycle.json` — статусы источников; только безопасные коды и счётчики.
- `.runtime/paused.json` — сохраняемая ручная пауза.

## Автоподъём Windows

Имя задачи: **`MailOrganizer.HiddenWorker`**.

Параметры:
- текущая учётная запись, обычные права, без пароля в задаче;
- запуск после входа в Windows, задержка 30 секунд;
- дополнительный триггер каждые 5 минут;
- restart after failure: 1 минута, 3 попытки;
- IgnoreNew: параллельные экземпляры задачи не создаются;
- внутри приложения дополнительный kernel mutex защищает от ручного двойного старта;
- исполняемый файл `.venv/Scripts/pythonw.exe`, без консоли;
- без ограничения длительности выполнения и без пробуждения ПК;
- ручная пауза сохраняется: задача может запускаться и спокойно завершаться, но не отменит `stop`.

При закрытии worker kernel освобождает mutex; «устаревший lock-файл» не мешает восстановлению. После сна цикл продолжится; пропущенные интервалы не превращаются в сотни повторных запусков.

**До входа пользователя в Windows эта конфигурация не работает.** Используется его Credential Vault. Физическая перезагрузка не проводилась; проверяются определение зарегистрированной задачи, её реальный запуск и отдельный тест аварийного завершения процесса.

## Авторизации

Токены и refresh-cache хранятся отдельно для Gmail-1/Gmail-2/Outlook-1 в Windows Credential Vault. Новый процесс загружает тот же cache. Перезагрузка сама по себе его не удаляет. Сбой обновления не перезаписывает исправный cache пустыми данными.

- **Google:** desktop OAuth, `gmail.readonly`, offline refresh. External application в режиме Testing выдаёт Gmail refresh token на 7 дней. Для длительного использования нужен корректный Publishing status/Production и повторная авторизация после перехода. Требования verification/ограничения personal-use зависят от приложения и аккаунтов; этот статус существующего клиента пока не проверен.
- **Microsoft:** MSAL public client, `Mail.Read` + `User.Read` для собственной identity, silent refresh и сохранение обновлённого cache. Отзыв доступа, корпоративные политики и interaction_required могут потребовать повторного consent.
- **Вечный доступ не гарантируется:** смена пароля, отзыв, политики провайдера и неиспользование могут инвалидировать refresh token. Код должен различать это и временную недоступность сети.
- Worker не открывает login/consent сам. Интерактивный `auth` вызывается отдельно, когда пользователь готов самостоятельно пройти вход.

Источники:
- https://developers.google.com/identity/protocols/oauth2
- https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens
- https://hermes-agent.nousresearch.com/docs/user-guide/features/cron

Hermes cron требует работающий gateway/планировщик. Поэтому он не выбран единственной гарантией подъёма после перезагрузки; глобальный gateway пользователя не меняется.

## Управление через Hermes — 4 действия

1. **«Почта, статус»**:
   ```bash
   .venv/Scripts/python.exe -E -X utf8 scripts/mail_commands.py status
   ```
2. **«Запусти почту»**:
   ```bash
   .venv/Scripts/python.exe -E -X utf8 scripts/mail_commands.py start
   ```
3. **«Останови почту»**:
   ```bash
   .venv/Scripts/python.exe -E -X utf8 scripts/mail_commands.py stop
   ```
4. **«Покажи разбор»** по уже сохранённым письмам:
   ```bash
   .venv/Scripts/python.exe -E -X utf8 scripts/mail_commands.py report
   ```

Это естественные запросы, не выдуманные встроенные `/mail` команды Hermes. Командный мост не исполняет произвольный shell и не принимает пароль/токен.

`check` — один ограниченный read-only цикл, не параллельно с активным worker. `tasks` — локальный экспорт структурированных заданий для модели, без отправки внешнему AI. Пакетные ответы модели валидируются отдельной командой `validate-results`.

`start` предпочитает совпадающую зарегистрированную задачу Windows: проверяет её executable и arguments, затем запускает именно её. Если такой задачи нет для этого конфига, используется прямой скрытый запуск, который подстраховывает соответствующий watchdog. Перезапуск через 1 минуту относится к аварии процесса, запущенного самой задачей Windows; общий дополнительный контроль — каждые 5 минут.

## Статусы — что они доказывают

- `running=true`, `heartbeat_fresh=true`: реальный процесс с совпадающим временем создания жив и пишет heartbeat.
- `stalled`: процесс жив, heartbeat устарел; это не считается нормальным состоянием.
- `auth_required`: аккаунт нужно авторизовать, не «вся система упала».
- `configuration_required`: не хватает конфигурации/разрешений, например публичного Microsoft client ID.
- `retry_later`: временная сеть/refresh/тайм-аут, следующая попытка автоматически в штатном цикле.
- `needs_attention`: ошибка не классифицирована однозначно, не выдаётся за успешную выгрузку.
- `bounded_scan_finished`: завершён ограниченный проход, НЕ полный архив.

Остановка не убивает чужие процессы. Если сейчас идёт выгрузка, graceful stop может дождаться текущей ограниченной команды; до завершения статус остаётся `stop_requested`. Тайм-аут команды — 180 секунд по умолчанию. Содержимое ошибок провайдера и токены в status не выводятся.

## Текущий охват

Интервал почтового прохода — 15 минут, лимит — 100 писем на аккаунт. Gmail query пустой (без фильтра периода, без Spam/Trash), Outlook — Inbox. Устойчивый полный backfill/history/delta всех папок ещё не реализован. PDF/DOCX/OCR, реестр дел по целой переписке и календарный writer также требуют следующих этапов.

При отсутствии авторизаций worker только фиксирует состояния ожидания. Реальные письма внешней модели не отправляются, почта не перемещается/удаляется, календарь не меняется.

## Переустановка задачи

Из корня проекта, после создания корневого venv. Для новой установки сначала создать конфигурацию без секретов (существующая не перезаписывается):

```bash
.venv/Scripts/python.exe -E -X utf8 -m mailorganizer.runtime init-config --config runtime.json --archive-root real-mail --state-dir .runtime
```

Затем зарегистрировать задачу:

```bash
powershell.exe -NoProfile -NonInteractive -File scripts/register_worker_task.ps1 -ProjectPath 'C:/path/to/mail-organizer' -ConfigPath 'C:/path/to/mail-organizer/runtime.json'
```

Существующую чужую задачу с тем же именем скрипт не перезаписывает. Task XML передаётся как Unicode string без противоречивой encoding declaration.

## Проверка

```bash
.venv/Scripts/python.exe -m pytest -q
```

Тесты включают synthetic источники, действительные скрытые процессы с отдельным временным конфигом, double-start, pause/resume, завершение собственного дерева при timeout и восстановление kernel lock после аварии. Это не доказательство авторизации реальных ящиков: для неё нужен отдельный live consent и read-only sync.
